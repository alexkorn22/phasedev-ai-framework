## Шаг 3. Решения фильтров — заделы (принято заранее)

**Переносятся (адрес — этот скилл, назначено ещё на этапах 0 и 3):**

- V99 — "Every finding requires evidence. No exceptions... Evidence format: `file_path:line_number` or `file_path:function_name:line_number`."
- V100 — "Findings without evidence are discarded. 'I believe there may be an issue' is not a finding."
- V102 — "Do not fabricate file paths or line numbers to fill evidence requirements."
- B46 — «уверенность измеряет, насколько ревьюер уверен, а не насколько проблема важна»: критичная по классу находка с низкой уверенностью не отбрасывается — верифицируется, затем репортится или отклоняется с опровержением.
- B47 — «pre-existing — не причина молчать»: находка вне диффа репортится как pre-existing debt с file:line, а не пропускается (согласуется с правилом забора в verification-method: не дубль — там про скоуп диффа, здесь про обязанность репорта).
- B45 (часть) — триаж по severity с обязательной верификацией при низкой уверенности. Формы «фиксить немедленно/бэклог» — сторона получателя; для ревьюера остаётся принцип «severity задаёт срочность, уверенность — только фильтр репорта».

**Ожидаемые применения стоящих конфликтов при сборке:**

- №2: числовые пороги размера (file-limits) — только вспомогательный сигнал ревьюера, не правило написания кода.
- №3: CQ-гейты — чеклист смыслов + evidence-стандарты; PASS/CONDITIONAL/FAIL-проценты и тиры не переносятся.
- №4: шкала S1–S4 не заводится; модель уверенности (0–25 отбросить / 26–50 не сообщать / 51+ сообщать) — фильтр перед репортом.

**Ожидаемые дедупы:** «ноль находок — валидный результат» (ECC) не дублировать с «не выдумывай находки» — одна формулировка; «zero findings on a 150+ line diff is suspicious» (zuvo) — дополняющая пара к ней, обе стороны нужны; evidence-стандарты не дублировать с verification-method (там — заявления о проверке, здесь — находки).

## Шаг 3 (продолжение). Решения по основному экстракту

**Фильтр 1 (lifecycle) — выбыли:** форматы отчётов (C23, C64–C65, C78-формы — поля находки сохранены как метод); CodeSift/PRECOMPUTED_DATA/провайдерская механика (C26 частично, C30, C85, C115); C43/C44 — когда ревью запускается, решает оркестратор/фреймворк; C126-прекондиции CI; C109-персистенс (механизм находок принадлежит фреймворку, принцип Zero Silent Discards сохранён).

**Стоящие конфликты применены:** №1 — «80% coverage minimum» (C126) отброшено; №2 — file-limits как вспомогательный сигнал в `references/size-thresholds.md` с явной пометкой «не правило написания»; №3 — CQ-смыслы в `references/quality-checklist.md`, скоринг-полосы не перенесены; №4 — модель уверенности 51+ вместо второй шкалы; словарь severity — MUST-FIX/RECOMMENDED/NIT (совпадает с zuvo C77, ECC-шкала не заводится).

**Разрешения противоречий доноров:** см. экстракт (5 разрешений: порог 51+ против ≥80; треугольник калибровки; отброс 0–25 при Zero-Silent-Discards >25; исключение confidence≠importance; словарь severity). «Err on the side of flagging» из plan-reviewer НЕ перенесён — прямая противоположность модели уверенности, контекст план-ревью.

**Дедупы:** C52 naming — dev-core (Ubiquitous Domain Language) уже несёт; C118/C119 evidence-стандарты — общая часть в verification-method, здесь finding-специфика; C121 — уже в design-fidelity-method; C40 верхняя половина (wording завершения) — verification-method; C92≡C114 схлопнуты; C126-чеклист ⊂ C63.

**Фильтр 3 — выбыли:** C25 (декларация роли), C45/C47/C49-обоснования порогов (историческая калибровка донора — суть в самих порогах), C86-механика маркера (принцип раскрытия самооценки сохранён строкой), C99/C129.5 (похвала — сохранена одна строка «признавай реальные улучшения» в секции обратной связи), C130 (комментарии — авторская сторона у dev-core Comment Rule).
